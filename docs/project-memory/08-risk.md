# Risk Register

| ID  | Risk                                                                                                                                                                                                                                                                                                                                  | Likelihood                                                         | Impact                                                                                                                                                                                                                                         | Mitigation / status                                                                                                                                                                                                                                                                        |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| R-1 | PostgreSQL may already be heavily represented elsewhere in the portfolio, undermining the "distinct technology coverage" goal this repo was asked to respect. This session's GitHub access was scoped to `arb-rajab/notifyhub` only, so the choice (ADR-006) could not be checked against sibling repos directly.                     | Medium                                                             | Low (doesn't affect notifyhub's own correctness, only portfolio-level coverage variety)                                                                                                                                                        | Documented plainly rather than guessed around. The coordinator session should check sibling repos' persistence choices and, if Postgres is indeed over-represented, treat this as a candidate to revisit before the portfolio is considered final — not a defect to fix unilaterally here. |
| R-2 | The in-memory `PubSub` (ADR-005) means real-time delivery only works correctly with exactly one running instance of notifyhub. A second instance would each maintain its own disconnected set of live subscriptions, and a notification published against one instance would never reach a subscriber connected to the other.         | Low today (single-instance is the only deployment target in scope) | High if ever scaled horizontally without addressing this first                                                                                                                                                                                 | Isolated behind the `PubSub` swap point documented in ADR-005; not fixed because nothing in this session's scope runs more than one instance.                                                                                                                                              |
| R-3 | The WebSocket transport has no per-connection or per-message rate limiting (only the HTTP `/graphql` endpoint does, via `express-rate-limit`). A malicious or buggy client could open many subscriptions or spam `connection_init` attempts.                                                                                          | Low (no public traffic yet)                                        | Medium                                                                                                                                                                                                                                         | Not mitigated in this session. Tracked in [09-backlog.md](./09-backlog.md).                                                                                                                                                                                                                |
| R-4 | JWTs cannot be revoked before their 15-minute expiry (ADR-003) — a compromised token remains valid until it naturally expires.                                                                                                                                                                                                        | Low (short expiry bounds the window)                               | Medium if a token is actually compromised                                                                                                                                                                                                      | Accepted tradeoff of the stateless-JWT decision; short default expiry is the mitigation in place. A refresh-token + revocation-list design is the documented future fix, not implemented (see [09-backlog.md](./09-backlog.md)).                                                           |
| R-5 | Docker build/run was never executed in this sandbox (no Docker daemon available), so the Dockerfile and docker-compose.yml are reviewed and believed correct but not empirically proven to build/run until CI's `docker` job runs.                                                                                                    | Medium until first CI run                                          | Medium (a broken image would block deploys, not break the API itself)                                                                                                                                                                          | `.github/workflows/ci.yml`'s `docker` job builds the `runtime` target on every push/PR. Check its status before trusting the image; this is the first real verification.                                                                                                                   |
| R-6 | N+1 query pattern in field resolvers (`Channel.owner`, `Notification.channel`/`author`, etc. — see [03-architecture.md](./03-architecture.md)) will show up as real latency under load with large result sets.                                                                                                                        | Low today (demo-scale data)                                        | Medium at larger scale                                                                                                                                                                                                                         | Accepted, documented tradeoff; DataLoader batching is the known fix, tracked in [09-backlog.md](./09-backlog.md), not implemented because current scope doesn't need it.                                                                                                                   |
| R-7 | GitHub-native Dependabot alerts (as opposed to `npm audit`, which was run and returned clean) could not be enumerated by any tool available in this session — there is no verified "zero Dependabot alerts" claim, only a verified "zero `npm audit` findings" claim.                                                                 | Unknown                                                            | Unknown until checked                                                                                                                                                                                                                          | `.github/dependabot.yml` is configured going forward. Whoever has GitHub UI/API access to this repo's Security tab should do one real check of the Dependabot alerts panel; this session could not.                                                                                        |
| R-8 | Real APNs device-push delivery (`ApnsPushChannel`, ADR-008) can never be verified end-to-end from this sandbox or from CI — it needs a real Apple Developer `.p8` key, Key ID/Team ID, and a physical iOS device, none of which can exist here by design (live push credentials must never sit in a repo or CI-readable environment). | Certain — this is a standing sandbox constraint, not a probability | Low for notifyhub's own correctness (protocol-level tests cover the HTTP/2 request/response contract, retry/backoff, and token invalidation against a real local server); the residual risk is entirely in the untested Apple-side integration | **Permanent, by design — not a gap to close in a future session.** Documented in ADR-008. Anyone needing live-delivery assurance must run notifyhub-ios on a physical device with real credentials outside any automated session.                                                          |
